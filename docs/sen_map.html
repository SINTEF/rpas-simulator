SEN in one minute

SEN is a distributed object middleware. Everything is an object with properties (state), methods (commands) and events (notifications). Objects live on buses, and SEN moves them between processes for you. Each process starts as sen run <config>.yaml, and the YAML says which packages to import, which components to build and which objects to put on which buses.

Writes land at commit

Each cycle runs drain → update() → commit. setNextX(v) stages a value that nobody sees until the commit, not even the object itself. getX() reads the frozen current value.

Everything is async

A method call returns at once. The result arrives in a callback one or two cycles later. With no callback, the result and any error are dropped.

Handles must stay alive

Subscriptions and connection guards are kept as members. When a handle is destroyed, SEN unsubscribes without a warning.

Processes and buses

One SEN kernel per process, one process per container. There are three kinds of bus: each drone has its own; objects that other drones or the ground station use share swarm.bus; and the world's truth sits on sim.bus.

The air link is an IP network below SEN: a mesh radio on a real system, the Docker network here. ether carries swarm.bus across it like any other bus. Link quality is not simulated.

drone<ID>.bus

one drone: core process + partner containers
  • Objects only this drone uses, such as flight_controller and sensor.
  • The same names on every drone. C++ never names a bus; it reads its droneBus static.
  • Isolation is by naming. SEN does not enforce it.

swarm.bus

drones, ground station, world/REST, partners
  • Per drone: drone<ID>, waypoint_navigator_drone<ID>.
  • The ground station: ground_station and fleet_status.
  • The UI commands drones only through this bus, by calling the drone's own objects (drone<ID>, waypoint_navigator_drone<ID>).

sim.bus

world process + airframes + simulated sensors
  • world holds sim time, time scale and pause.
  • Ground assets and one truth_drone<ID> per drone.
  • The UI renders from here but never commands through it.

Where an object lives, and its name

The rule: an object goes on swarm.bus if another drone or the ground station calls or reads it. Everything else stays on drone<ID>.bus. flight_controller and sensor never go on swarm.bus.

Names: on the drone bus a name is the same on every drone. On swarm.bus names must be unique, so the YAML appends the drone, and the object gets a droneId static:

- name: waypoint_navigator_drone@env(DRONE_ID)   # → waypoint_navigator_drone1
  class: waypoint_navigator.WaypointNavigatorImpl
  bus: swarm.bus
  droneBus: drone@env(DRONE_ID).bus              # where it finds flight_controller
  droneId: "@env(DRONE_ID)"

C++ never builds or parses a name. It asks for all objects of a class and picks one by droneId. Here is how a node on another drone would send drone 2 a route:

// registered(): one interest for the class on swarm.bus
navigatorSub_ = api.selectAllFrom<drone_sim::WaypointNavigatorInterface>(getSwarmBus());

// later: the WaypointNavigator whose droneId is "2"
for (auto* navigator : navigatorSub_->list.getObjects())
  if (navigator->getDroneId() == "2") navigator->setRoute(route, speed, callback);

Other drones' telemetry works the same way: the DroneLink objects on swarm.bus, skipping your own droneId. A new cross-drone message is just a method on the node's own .stl.

Inside one drone

A drone's core container runs sen run config/drone.yaml. Components start in ascending group order and stop in descending order, so the nodes start after the airframe. Discovery is still asynchronous, so a node's subscription list can be empty for a few cycles, and the code handles that.

Compiled nodes and container images

Every piece of on-board software is a SEN object made by compiled C++. What differs is where that code is packaged and which process runs it.

Our nodes: packages in the core

Each node is a C++ package (add_sen_package) compiled to a shared library and baked into the drone_sim/sim image.

sen run config/drone.yaml loads the packages listed under imports: into one process. They share one kernel, and each component gets its own thread.

Adding a node means one YAML block and a rebuild of our image.

Partner nodes: their own image

A partner ships a Docker image (or source that we build into one), e.g. partner/geocage. It is built against the partner SDK in /opt/drone_sim.

It runs its own sen run with its own YAML, so it is a separate process with its own kernel.

It uses the buses the same way our nodes do, carried by ether.

SEN hides the difference. A node reading flight_controller gets the same interface whether the object is in its own process or another container. The only visible difference is a little more latency.

One compose project per drone

Each drone is one Docker Compose project: docker/drone.compose.yml, started as project drone<ID>. It holds the core container plus that drone's on-board partner containers.

Partner containers set network_mode: service:core, so they share the core's network and start and stop with it. SEN knows nothing about it: to SEN these are just processes that open the same drone<ID>.bus.

The contract layer

An .stl that other packages use across a bus is a contract in interfaces/; anything only one node uses stays in its own package.

  • drone_bus/flight_controller.stl: state : VehicleState, one struct, so every snapshot is consistent, plus arm, takeoff, goToPosition, land and more. Each returns CommandAck.
  • swarm_bus/waypoint_navigator.stl: the navigator's contract, with a droneId static. Its package has no STL_FILES of its own.
  • swarm_bus/drone_link.stl: the vehicle's public face. droneId, envelope, heartbeat, telemetry and the six flight-controller commands.
  • Packages extend contracts for simulator-only settings. SimAirframe : extends FlightController adds simBus, publishRate and the fixed-wing limits (bank, flight-path angle, loiter radius), and a typed interest on FlightController still finds it.

Anything that changes state across a bus is a method returning CommandAck, never a property write. Type changes do not work across processes built from different versions (SEN converts types with silent data loss), so rebuild and restart everything together.

A command, end to end

Here is setRoute sent from the UI to drone 1. The UI calls the drone's own object directly; there is no router or bridge in between.

  1. Browser → world process
    A REST invoke of swarm.bus/waypoint_navigator_drone1.setRoute(route, 0), handled by the rest component.
  2. World → drone 1 core process over swarm.bus
    Ether delivers the call to WaypointNavigatorImpl::setRouteImpl.
  3. Navigator → flight_controller.goToPosition() on drone1.bus
    Called once per waypoint. The navigator found flight_controller with an interest on its droneBus.
  4. The CommandAck goes back the same way
    The navigator's ack returns to the UI. The UI reads status and currentIndex from waypoint_navigator_drone1 itself.
Known SEN bug at the pin

One interest per class, per shared bus, per process

At 05da288e, if two different interests in one process match the same remote object, that object stops updating for that process about 5 seconds later and stays frozen.

So the REST clients use a single SELECT * FROM <bus> and dispatch on class name. In each drone process, all components use the identical query per class on swarm.bus and filter by droneId in code, never with WHERE. Drone buses are not local either, so the rule applies there too.

Build glue

Each package is one add_sen_package call. DEPS drone_sim_interfaces brings in the shared contract types and their generated headers.

add_sen_package(
  TARGET waypoint_navigator
  SOURCES src/waypoint_navigator_impl.h src/waypoint_navigator_impl.cpp
  # No STL_FILES: the interface is the WaypointNavigator contract in interfaces/
  DEPS drone_sim_interfaces drone_sim_common
  SCHEMA_PATH ${CMAKE_CURRENT_BINARY_DIR}
)
  • Each *_impl.cpp ends with SEN_EXPORT_CLASS(XImpl). Without it, startup aborts with "Type was not registered."
  • The YAML class: is <package>.<ImplName>, e.g. waypoint_navigator.WaypointNavigatorImpl.
  • YAML keys under an object map one-to-one to [static] properties, such as droneBus, droneId and publishRate.
  • An object on swarm.bus or sim.bus opens its drone bus in its first update(), never in registered(): SEN holds the object's bus lock there, and the reverse order deadlocks the process.
